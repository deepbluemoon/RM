# 브랜치·머지 전략

계약위험탐지(RM) 프로젝트의 브랜치 운영과 병합 규칙이다. 브랜치 전략은 "어떻게 갈라지나", 머지 전략은 "어떻게 다시 합쳐지나"를 정하며 한 쌍으로 적용한다. 루트 AGENTS.md와 docs/01-issue-template/GUIDE.md의 작업·검증·push 규칙을 따른다.

## 전제

- 장기 브랜치는 `main` 하나다. `main`은 항상 검증 가능한 상태를 유지한다.
- AI와 사람이 이슈 템플릿(feature_request / bug_report / runtime_readiness) 기반으로 작업한다.
- 릴리스 주기가 분리되어 있지 않으므로 Git Flow(`develop`/`release`/`hotfix`) 대신 **GitHub Flow**(`main` + 단기 토픽 브랜치)를 채택한다.

## 브랜치 전략

### 기준 브랜치

- `main`: 기본 브랜치이자 유일한 장기 브랜치. 직접 push를 금지하고 토픽 브랜치의 병합으로만 갱신한다.

### 토픽 브랜치

- `main`에서 분기하고 작업 단위(이슈 하나)당 하나를 만든다. 수명은 짧게 유지한다.
- 네이밍은 이슈 유형과 연결한다.

| 접두 | 용도 | 대응 이슈 템플릿 |
|---|---|---|
| `feat/<요약>` | 기능 개발·개선 | feature_request |
| `fix/<요약>` | 오류 수정 | bug_report |
| `investigate/<요약>` | 최소 구동·실행 환경 조사 | runtime_readiness |
| `docs/<요약>` | 문서 작업 | — |
| `chore/<요약>` | 설정·정리 등 | — |

- 브랜치와 PR에는 관련 이슈 번호를 참조한다(`#1` 형식).
- GUIDE.md 규칙대로 **기존 브랜치를 임의로 삭제하지 않으며**, 겹치지 않는 이름으로 만든다.

### 브랜치 수명

1. 이슈 선택 → `main`에서 토픽 브랜치 분기
2. 작업·커밋
3. PR 생성 → 리뷰·검증
4. `main`으로 병합
5. 병합 후 브랜치 정리는 담당자 확인 후에만 수행

## 머지 전략

### 채택 방식

- **3-way merge 알고리즘 기반의 no-fast-forward 병합 커밋 방식(`--no-ff`)을 채택한다.**
- 3-way merge는 공통 조상과 양쪽 브랜치 끝 세 지점을 비교하는 Git의 병합 알고리즘이며, Git이 병합 시 기본으로 사용한다. 여기서 선택하는 것은 그 결과를 이력에 남기는 방식이다. `--no-ff`는 병합 커밋을 생성해 토픽 브랜치의 작업 이력을 보존한다.
- 이슈·PR 단위로 "무엇을, 왜, 어떤 검증으로 합쳤는지"를 추적하기 위해 이력을 압축하는 Squash나 선형화하는 Rebase/Fast-forward 대신 병합 커밋 방식을 사용한다.

### 병합 규칙

1. **병합 경로**: 토픽 → `main` 한 방향. `main` 직접 push 금지.
2. **PR 필수**: 모든 병합은 PR을 거친다. 리뷰·승인 주체와 셀프 병합 허용 여부를 사전에 정한다.
3. **병합 전 완료 조건**: GUIDE.md의 상태(통과 / 실패 / 미실행 / 차단 / 해당 없음)와 VERIFY.md 근거가 충족되어야 병합한다. 필수 검증이 남은 상태로 병합하지 않는다.
4. **충돌 해결**: 토픽 브랜치에서 최신 `main`을 먼저 반영한 뒤 충돌을 해소한다. 해소 책임은 토픽 브랜치 작업자에게 있다.
5. **커밋·병합 메시지**: 기존 접두(`feat:`, `fix:`, `docs:` 등)와 이슈 번호 참조를 사용한다. AI 작업 커밋은 지정된 Co-Authored-By 규칙을 따른다.
6. **병합 후 처리**: 브랜치 삭제는 GUIDE의 삭제 금지 원칙과 정합하게 담당자 확인 후 수행한다. push는 사용자의 명시적 지시 후에만 실행한다.

### 금지 사항

- `main` 강제 push 및 히스토리 변경(force-push, 되감기) 금지.
- 운영 비밀값·계약서 원문·개인정보를 커밋·이슈·PR에 포함 금지(AGENTS.md).
- 필수 검증 미완 상태를 완료로 표시하고 병합하는 것 금지.

## 요약

- 브랜치: `main` + 단기 토픽 브랜치(GitHub Flow), 이슈 유형별 네이밍.
- 머지: 3-way 기반 `--no-ff` 병합 커밋, PR·검증 완료 후 `main`으로만 병합.
- 공통: `main` 보호, 기존 브랜치·사용자 변경 보존, push는 명시 지시 후.
