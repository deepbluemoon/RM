# 설계 이유와 유지보수 기준

## 탐지 프로젝트에 맞춘 세 가지 양식

- 기능 개발·개선: 사용자 동작·인수 조건·API 계약·탐지 품질의 비교 기준을 정한다.
- 기능 오류: 비식별 재현 입력·관찰 사실·원인 가설과 오류 및 정상 사례의 회귀 결과를 연결한다.
- 최소 구동 점검: 작업 유형과 구동 범위를 선택하고 필요한 코드·설정·DB·모델·근거 데이터의 최소 조건을 판정한다.

입력·비식별화·M1·M2 탐지·근거 검색·설명·이력·권한은 영향 영역을 고르는 기준이다. 모든 이슈에서 모든 영역을 검사하라는 뜻은 아니다. specs/002-contract-risk-detection/의 현재 명세·계약과 실제 코드로 범위를 정한다.

## 조사와 구현의 완료 기준

최소 구동 조사는 의존성·부족한 조건·후속 조치를 찾는 작업이다. 설치나 기동을 완료 조건으로 강제하면 요청 범위를 벗어난다. 구현·검증 작업은 선택한 범위의 실제 결과가 필요하다. 이를 양식과 GUIDE에서 구분했다.

기존 SSH 경로·백업 후보·과거 파일 일치 수치는 기본 조건에서 제거했다. 컨테이너 전환도 별도 요청이 있을 때만 포함한다.

## 검증 근거와 탐지 품질

체크박스만으로 성공을 판단하지 않는다. 통과는 관찰 근거와 연결하고 차단·해당 없음은 이유를 남긴다. 스텁·heuristic·실모델을 구분하고, 탐지 품질 변경은 평가 사례·버전·지표·허용 기준을 먼저 정한다. /health나 /v1/models 응답만으로 분석 품질을 보장할 수 없으므로 실제 분석 결과도 확인한다.

## 적용본과 사본

GitHub 적용 대상은 .github/ISSUE_TEMPLATE/의 이슈 양식과 .github/pull_request_template.md의 공통 PR 본문이다. changes와 completed는 같은 상대 경로의 전달·검토용 사본이다. 적용 대상 파일 기준으로 함께 갱신하고 파일별 해시를 대조한다. 확인하지 않은 라벨·담당자는 강제하지 않는다.

PR 제목 형식은 CONTRIBUTING.md, 본문 양식은 .github/pull_request_template.md에서 관리한다. docs/01-issue-template/PR.md는 과거 작업의 본문 예시로 보존한다. Markdown PR 템플릿은 제목을 자동 입력하거나 필수 항목·승인 인원을 강제하는 설정이 아니다. 기본 브랜치에 반영되기 전에는 GitHub 적용 완료로 기록하지 않는다.

이슈 양식은 작성 가이드이며 필수 입력을 기술적으로 강제하지 않는다. AI 작업 시 GUIDE와 선택한 이슈의 범위·인수 조건을 함께 제공한다. 반복 사용 중 누락이 발생하면 양식과 검증 기준을 함께 보완한다.
