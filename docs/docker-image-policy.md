# Docker 이미지 규약 제안

이 문서는 계약위험탐지 서비스의 FastAPI 모델 게이트웨이(`model-server`) 이미지에 대한 **팀 검토용 제안**이다. 합의 전에는 확정된 운영 정책이나 구현·검증 완료 근거로 취급하지 않는다. 이미지 구현은 별도 작업에서 범위와 인수 조건을 정한다.

## 1. 목적과 적용 범위

팀원이 같은 기준으로 이미지를 빌드하고 실행 결과를 추적할 수 있도록 이름, 구성, 실행 조건과 검증 기준을 정한다. 첫 적용 대상은 모델 게이트웨이이며, 백엔드·프런트엔드 이미지는 필요할 때 별도로 정한다. Dockerfile은 이미지 빌드 방법을, 실행 설정은 포트·환경변수·마운트 등 배포 환경별 값을 담당한다.

현재 [배포 안내](../deploy/README.md)는 Docker를 사용하지 않는 macOS 구성을 설명한다. 이 제안이 기존 배포 환경을 변경하지는 않는다.

## 2. 이름과 버전

- 이미지 이름은 `<registry>/<namespace>/rm-model-server` 형식을 제안한다. registry와 namespace는 팀이 실제 사용할 값으로 정한다.
- 개발 빌드 태그는 `sha-<Git 커밋 SHA 앞 12자리>`를 사용한다. 릴리스 태그는 `0.1.0`처럼 버전을 사용하고 배포한 릴리스 태그를 덮어쓰지 않는다.
- 태그는 사람이 찾기 위한 이름이다. 배포 기록에는 실제 이미지 digest와 소스 커밋을 함께 남기고, 롤백 시 이전에 검증한 digest를 사용한다.
- 실제 운영할 CPU 아키텍처(`linux/amd64` 또는 `linux/arm64`)를 기록하고 해당 플랫폼에서 검증한다. 지원하지 않거나 검증하지 않은 플랫폼은 성공으로 표시하지 않는다.

## 3. 빌드와 이미지 구성

- Python 버전은 [pyproject.toml](../model-server/pyproject.toml)의 `>=3.11,<3.12` 조건을 따른다. 베이스 이미지는 필요한 운영체제 라이브러리와 호환되는 Python 3.11 slim 계열을 우선 검토하고, 버전·배포판·digest를 고정한다. 보안 갱신 시 새 digest로 변경하고 다시 검증한다.
- `uv.lock`을 사용하여 의존성을 설치한다. 실모델용 이미지는 `uv sync --frozen --no-dev --extra classifiers`를 기준으로 하며, 선택한 플랫폼에서 PyTorch 설치와 실행을 확인한다. 개발·학습 도구는 운영 이미지에 포함하지 않는다.
- 필요한 경우 멀티스테이지 빌드로 빌드 도구와 실행 파일을 분리한다. 재현성과 호환성을 해치지 않는 범위에서 이미지 크기를 줄인다.
- 저장소 루트를 빌드 컨텍스트로 사용하는 구성을 권장한다. `model-server/config.yaml`은 `../shared/assertion-terms.json`을 참조하므로 이미지에 두 경로의 관계를 유지하거나 설정 경로를 명시적으로 지정한다. 코드 외에 설정, 스키마, 모델 메타데이터 등 실제 실행에 필요한 파일을 확인해 복사한다.
- `.dockerignore`로 `.git`, `.venv`, 캐시, 로그, `.env` 및 기타 비밀 파일, 불필요한 학습 데이터와 모델 가중치 등을 빌드 컨텍스트에서 제외한다. 필요한 파일이 제외되지 않았는지 확인한다. `.dockerignore`만 믿지 않고 이미지에도 필요한 파일만 명시적으로 복사한다.
- 운영 비밀값, 실제 계약서 원문과 개인정보는 이미지 레이어나 빌드 인자에 넣지 않는다. 빌드 과정에서 비밀값이 필요하면 안전한 비밀 전달 방식을 별도로 정한다.

## 4. 모델 자산과 외부 서비스

- M1·M2 가중치는 이미지 밖에서 제공하고 읽기 전용으로 마운트하는 구성을 우선한다. `MODEL_ROOT`를 컨테이너 안의 모델 디렉터리로 지정한다. 가중치뿐 아니라 모델 카드·토크나이저·설정 등 필요한 파일도 함께 제공한다.
- 배포 기록에 이미지 digest와 함께 모델 자산의 버전·체크섬 및 필수 파일 목록을 남긴다. Git LFS 포인터만 존재하는 상태는 가중치 준비 완료가 아니다. 현재 `models.lock.yaml`을 M1·M2 전체 자산의 잠금 목록으로 간주하지 않는다.
- M3·M4는 기존 공유 Ollama를 사용한다. 컨테이너 기동 과정에서 Ollama 서버를 띄우거나 모델을 다운로드·등록하지 않는다. [공유 Ollama 가이드](ollama-guide.md)의 호출·자원 사용 제한을 따른다.
- 현재 설정의 `127.0.0.1:11434`는 컨테이너 내부를 가리킨다. `OLLAMA_URL`에 배포 환경에서 접근 가능한 주소를 지정하고 실제 연결을 확인한다. Docker 네트워크에서 호스트로 접근하는 방법은 플랫폼별로 확인한다.

모델 파일 또는 분류기 의존성이 없으면 현재 코드가 heuristic으로 동작할 수 있다. 실모델용 배포의 검증에서는 이 상태를 성공으로 인정하지 않는다. 개발용 heuristic 구성은 명시적으로 구분한다.

## 5. 실행과 보안

- 고정된 UID/GID의 일반 사용자로 실행하고 모델 및 필요한 설정 파일의 읽기 권한을 확인한다.
- 컨테이너 내부 Uvicorn은 `0.0.0.0:9542`, worker 1개로 실행하는 구성을 권장한다. 개발용 reload는 운영에서 사용하지 않는다. 호스트에 공개할 주소와 포트는 실행 설정에서 제한한다.
- 현재 Ollama 동시 호출 제한은 게이트웨이 프로세스 내부에서 적용된다. 공유 서버의 동시 호출 1건을 유지하도록 초기 배포는 게이트웨이 인스턴스 1개를 권장한다. 확장할 때는 인스턴스 간 제한 방법을 먼저 검토한다.
- `MODEL_API_KEY` 등 비밀값은 실행 환경에서 주입한다. 키는 백엔드와 일치해야 하며 이미지, 저장소, 예시 값, 로그에 실제 값을 남기지 않는다.
- 로그는 표준 출력·표준 오류로 내보내고 요청·응답 본문, 계약서 원문과 인증 정보를 기록하지 않는다. 기존 [모델 서버 안내](../model-server/README.md)의 로그 원칙을 따른다.

## 6. 검증 및 기록

구현 이슈에서 대상 플랫폼, 모델 자산, 외부 서비스 접근과 필수 인수 조건을 먼저 정한다. 다음 검증을 해당 범위에 맞게 실행하고 명령·대상 버전·결과를 작업 기록이나 PR에 남긴다.

1. 지정 플랫폼에서 잠금 파일로 빌드하고 이미지 digest를 기록한다.
2. 일반 사용자로 기동해 설정·스키마·공용 파일·읽기 전용 모델 경로 접근을 확인한다.
3. 인증 실패와 인증된 `/health` 응답을 확인한다. `/health`의 `loading`·`degraded` 및 HTTP 상태는 [모델 API 계약](../specs/002-contract-risk-detection/contracts/model-api.openapi.yaml)에 따라 해석한다. `cold`는 호출 가능한 상태다.
4. 실모델을 범위에 포함하면 인증된 `/v1/models`에서 기대한 M1·M2 모델과 버전을 확인하고 가상 조항으로 실제 추론한다. `/health` 성공이나 모델 파일 존재만으로 실모델 성공을 판정하지 않는다.
5. 외부 연동을 범위에 포함하면 공유 Ollama 연결과 M3·M4 호출을 확인한다. 공유 서버 사용 규칙과 기동 시 예열 영향을 고려한다.
6. 이미지와 빌드 산출물에 비밀값, 실제 계약서 원문, 불필요한 데이터가 없는지 확인한다.

결과는 [작업 안내](01-issue-template/GUIDE.md)에 따라 통과 / 실패 / 미실행 / 차단 / 해당 없음으로 구분한다. 정적 확인·스텁·heuristic·실모델 결과를 구별하고, 실행하지 않은 검증을 성공으로 표시하지 않는다. CI 자동화, 이미지 레지스트리, 배포 및 취약점 검사 도입 여부는 별도 작업에서 정한다.

## 7. 합의가 필요한 항목

- 사용할 registry와 namespace, 태그 발급·보존·삭제 방식.
- 첫 배포 플랫폼과 환경별 포트 공개 범위.
- 모델 자산 제공 위치, 체크섬 관리 방법과 접근 권한.
- 베이스 이미지 갱신 주기, 취약점 점검 및 예외 처리 담당.
- 자동 빌드·검증 도입 시점과 릴리스 승인 방식.

참고: [Docker 빌드 모범 사례](https://docs.docker.com/build/building/best-practices/), [uv의 Docker 사용 안내](https://docs.astral.sh/uv/guides/integration/docker/).
