====================================================

runbook.txt 파일의 목적 

1. 우리가 어떤 프로젝트를 진행하고 있는지 설명한다.
2. 우리가 어떤 작업을 진행했고, 과정에서 어떤 어려움이 있었는지 기록한다.
3. 장애 및 이슈 발생 시 해결 후 작성 가이드에 따라 기록한다.
4. 가이드에 기록된 장애 및 이슈 발생 시 해당 파일의 기록을 가장 먼저 시도해본다.

=====================================================

runbook 작성 가이드

runbook에 내용을 추가 할 때 가장 처음에 발생일시 혹은 인지한 시간을 적는다.
기억이 나지 않는다면, 날짜까지만 적도록 한다.

해결과정을 상세하게 적는다. 
어떤 기술을 어떻게 사용했고, 어떤 명령어를 사용했는지 적는다.
무엇을 가장 먼저 확인하고 수정했는지 적는다.

육하원칙에 의거하여 작성하고, 각 부분은 상세하게 기록한다.

## 2026-11-03 로컬 Compose 기동: 모델 서버 설정과 초기 임베딩 실패

### 상황 및 영향

Docker Hub 날짜 태그(`20261103`)로 로컬 Compose를 처음 실행했다. 프런트엔드와 백엔드, MariaDB, Ollama, 모델 서버는 기동했지만, 초기 벡터 적재용 `backend-embed`가 종료 코드 1로 끝났다. 따라서 서비스 화면은 `http://localhost:8080`에서 열리고 백엔드·MariaDB·Ollama·모델 서버 healthcheck도 통과하지만, 초기 근거 벡터 적재까지 완료된 상태는 아니다. 임베딩이 없는 검색은 코드상 BM25로 처리된다.

### 확인 과정과 원인

1. `docker compose ps --all`로 서비스별 상태를 확인했다. `backend-init`은 `Exited (0)`, `backend-embed`는 `Exited (1)`이었다.
2. `docker compose logs --tail=60 model-server`에서 모델 서버가 재시작하는 것을 확인했다. `.env`에 `LLM_PROVIDER`가 두 번 선언되어 두 번째 값이 `vertex` 설정을 덮고 있었다.
3. `.env`에는 `LLM_PROVIDER=vertex` 한 줄만 남기고 중복 줄을 제거했다. 잘못된 설정값이 컨테이너 로그에 기록되어 `MODEL_API_KEY`도 새 난수 값으로 교체했다. 비밀값 자체는 이 기록에 넣지 않는다.
4. 모델 서버 재기동 후 healthy 상태를 확인했다.
5. `docker compose logs --tail=60 backend-embed`에서 아래 오류를 확인했다.

   ```text
   Error: Cannot find module '/app/backend/scripts/embed-evidence.js'
   ```

6. `docker run --rm --entrypoint sh moonsangjin/tamji:be-20261103 -c 'test -f /app/backend/scripts/embed-evidence.js'`로 backend 날짜 이미지 안에 스크립트가 없는 것을 확인했다. 로컬 저장소에는 `backend/scripts/embed-evidence.ts`가 있고 현재 `backend/Dockerfile`은 이를 빌드·복사하도록 되어 있다. 이미지가 만들어진 소스 커밋 `56e50dd7831b`의 Dockerfile에는 해당 스크립트가 포함되지 않아, 이미지와 현재 저장소 코드의 산출물이 일치하지 않는 것이 원인이다.

### 조치 및 현재 상태

- 중복 `LLM_PROVIDER` 설정 제거, 공급자를 `vertex`로 정리, `MODEL_API_KEY` 교체 후 `backend`, `model-server`, `backend-embed`를 재기동했다. 이후 모델 서버와 백엔드 healthcheck가 통과했다.
- 프런트엔드 응답은 `curl -sS -o /dev/null -w '%{http_code}' http://127.0.0.1:8080`으로 HTTP 200을 확인했다.
- Docker Hub의 `be-20261103` 태그 자체는 수정하지 않았다. 아래 로컬 오버레이로 현재 저장소의 backend Dockerfile을 사용해 초기 적재를 해결했다. Docker Hub 이미지만으로 같은 상태를 재현하려면 `backend/Dockerfile` 수정이 포함된 이미지 세트를 새 불변 날짜 태그로 발행해야 한다.

### 이미지 갱신 후 재검증

```bash
docker compose pull
docker compose up -d
docker compose ps --all
docker compose logs --tail=60 backend-embed
```

완료 조건은 `backend`, `model-server`, `mariadb`, `ollama`가 healthy이고, `backend-init`과 `backend-embed`가 모두 `Exited (0)`인 것이다. DB 볼륨을 보존해야 하므로 이 문제를 해결할 때 `docker compose down -v`는 실행하지 않는다.

### 로컬 이미지로 복구 및 확인

`backend/Dockerfile`은 `embed-evidence.ts`를 컴파일하고 운영 스크립트 디렉터리에 복사한다. 아래 로컬 오버레이는 백엔드 세 서비스와 프런트엔드만 로컬 이미지로 바꾸며, MariaDB·모델 서버·Ollama는 날짜 태그 이미지를 계속 사용한다.

```bash
docker build -f backend/Dockerfile -t tamji-local/backend:local .
docker build -f frontend/Dockerfile -t tamji-local/frontend:local .
docker compose -f compose.yaml -f compose.local.yaml up -d
docker compose -f compose.yaml -f compose.local.yaml ps --all
```

2026-11-03 실행 결과: `backend-init`은 `Exited (0)`, `backend-embed`도 `Exited (0)`이었다. 임베딩 로그는 활성 기준일 1에서 bge-m3 벡터 45건 적재, 남은 항목 0건을 보고했다. 데이터는 MariaDB `evidence_embedding` 테이블에 저장되고 기존 `rm_db-data` named volume에 보존된다. 별도 파일 볼륨은 만들지 않는다.

서비스 화면은 `http://localhost:8080`에서 HTTP 200을 확인했다. 독립 운영 대시보드는 `npm run dev --prefix ops-dashboard`로 실행하고 `http://127.0.0.1:9760`에 접속한다. 대시보드는 인증이 없으므로 loopback 주소에서만 수신한다.

## 2026-11-03 위험조항 찾기 화면이 멈춘 것처럼 보임

### 상황 및 원인

분석 요청 1은 2026-11-03 14:05:58(KST)에 시작했고 14:07:00(KST)에 취소 요청이 들어왔다(약 62초). 백엔드 로그에는 `/api/analyses/1/cancel`이 HTTP 200으로 기록됐다. 이후 모델 서버의 해당 M1·M2 job은 53/53 조항을 오류 없이 완료했지만, 취소된 실행은 DB에서 `aborted`였고 점수가 저장되지 않은 53개 행이 `pending`으로 남아 있었다. 서버 오류나 모델 추론 실패가 아니라, 배치 결과가 DB에 반영되기 전에 사용자가 취소한 상황이었다.

탐지 화면은 `v_run_progress.scored_cnt`(DB에 저장된 점수)만 보여 줬다. M1·M2가 현재 문서의 배치 처리를 마칠 때까지 이 수가 바뀌지 않아 화면이 정지한 것처럼 보일 수 있었다. 브라우저 요청 기록상 상태 폴링은 계속 성공했고, 서버의 취소 요청이 분석을 중단했다.

### 수정 및 검증

- 분석 상태 API가 모델 서버의 현재 job에서 `done/total/status`를 읽어 현재 문서 진행률을 반환하도록 했다. 화면에는 현재 문서 진행률과 DB에 저장 완료된 전체 조항 수를 구분해 표시한다.
- 취소 직후 모델 서버 응답을 처리하지 않도록 중단 신호를 다시 확인하고, 취소 후에도 남은 `pending` 행을 `unanalyzable`로 정리하도록 했다.
- 실행 검증은 기존 요청을 재사용하지 않고 M1·M2 job 상태와 요청 로그를 읽어 수행했다. 해당 job은 `done`, 53/53, 오류 0건이었다. 이전 실행은 사용자가 취소했으므로 자동 재개하지 않는다.
- 현재 워크스페이스에는 수정 코드가 반영됐다. 실행 중인 컨테이너에 적용하려면 백엔드·프런트엔드 이미지를 로컬 빌드하고 `compose.local.yaml`을 적용한 뒤 다시 접속한다. DB named volume은 유지한다.

```bash
docker build -f backend/Dockerfile -t tamji-local/backend:local .
docker build -f frontend/Dockerfile -t tamji-local/frontend:local .
docker compose -f compose.yaml -f compose.local.yaml up -d
docker compose -f compose.yaml -f compose.local.yaml ps --all
```
