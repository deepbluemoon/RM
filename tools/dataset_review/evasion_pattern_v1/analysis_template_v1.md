## 1. 분석 범위와 방법

**대상.** 전자상거래 도메인 조항 463행 중 `label_status=official` 455행(35개 사건)입니다. 도메인 사건 36건 중 1건은 official 조항이 없습니다. 전체 공정위 사례(934개 official)는 참고 규모만 12절에 적었고 코딩하지 않았습니다.

**읽는 방식.** 공정위 판단 이유가 쟁점 단위로 공유되므로 조항을 쟁점(issue_unit_id) 261개로 묶어 모두 읽었습니다. 조항 원문(`problem_clause`)과 공정위 근거(`official_reason`, `action_or_outcome`)는 따로 읽고 따로 기록했습니다.
- 판정의 근거는 **조항 문언**입니다.
- 공정위 판단 이유는 그 문언이 어떻게 작동하는지 이해하는 데만 썼습니다.

**패턴 도출.** 키워드 빈도로 정하지 않았습니다. 조항마다 "무엇을 인정하고, 어떤 장치로, 무엇을 제한하는가"를 적어 두고 같은 작동 구조를 묶었습니다. 요청서에 예시로 제시된 구조는 데이터에서 확인된 것만 남겼고, 데이터에서 새로 나온 구조를 추가했습니다.
- 확인된 예시 구조:
  - 짧은 기간 → EP01
  - 과도한 비용 → EP03
  - 승인·재량 → EP10
  - 증빙·절차 → EP06
  - 예외 무력화 → EP05
  - 책임 전가 → EP12
  - 간주 동의 → EP08
  - 형식적 선택권 → EP14
- 데이터에서 새로 나온 구조:
  - 이용 트리거 → EP02
  - 환급 수단·시기 → EP04
  - 관할 → EP07
  - 형식적 고지 → EP09
  - 책임 요건 가중 → EP11
  - 부수 손실 → EP13

**반례.** 반례는 공정위 시정 과정에서 사업자가 고치고 공정위가 받아들인 "시정 후 약관조항"과 판단 이유 문장에서만 가져왔습니다. 만들어낸 사례는 없습니다. 현재 데이터에는 **공정위 심사를 받지 않은 정상 약관의 반례가 없다**는 한계가 있습니다(10절).

**코딩.** 분석자 1인이 판정했습니다. 코딩 원본은 `tools/dataset_review/evasion_pattern_v1/coding_v1.txt`에 있습니다. 빌드 스크립트가 다음 세 가지를 검증합니다.
- 455개 조항이 모두 정확히 한 번씩 코딩됐는지
- 존재하지 않는 ID가 없는지
- 원천 CSV의 SHA-256이 `TRANSFER_MANIFEST.json`과 같은지(수정 여부 점검)

## 7. 기존 issue_category와 회피패턴의 관계

기존 `issue_category`는 **무엇이 제한되는가(위험유형)**를, 회피패턴은 **어떻게 제한하는가(장치)**를 가리킵니다. 두 축은 1:1로 대응하지 않으므로 issue_category를 회피패턴 정답으로 쓸 수 없습니다.

{{TABLE_CATEGORY}}

- **refund_withdrawal_restriction**: 가장 다양한 장치가 모이는 유형입니다(EP01·02·03·04·05·06·10·13·14). "환불 제한"이라는 한 라벨 안에 직접 환불 금지와 비용·기간·절차를 통한 실질 제한이 섞여 있습니다.
  - 이 유형에는 사업자 해지·제재 조항 15건(D_POWER)도 들어 있습니다. 기존 분류가 쟁점 제목 기준이라 생긴 노이즈입니다.
- **liability_exemption**: 대부분 직접 면책입니다. 회피 구조는 EP11(책임 요건·한도)과 EP12(이용자 의무 전가, 대부분 불확실)에 몰립니다.
- **jurisdiction_dispute**: 거의 전부 EP07입니다. 소송 포기·집단소송 포기 조항만 직접형입니다.
- **deemed_consent_auto_renewal / terms_change_notice**: EP08(간주)과 EP09(형식적 고지)가 거의 전부입니다. 위험유형과 장치가 사실상 같은 축입니다.
- **user_content_rights, unilateral_termination**: 대부분 직접형(광범위 라이선스, 재량 삭제·해지)입니다. 예외는 두 가지입니다.
  - 게시를 허락으로 간주하는 조항(EP08)
  - 탈퇴를 전화로만 받는 조항(EP06, unilateral_termination로 분류됨)
- **settlement_fee, rights_restriction**: 정산·환급 보류(EP04)와 수수료(EP03)가 많습니다. 판매자 정산 보류는 법령 근거·부정거래 방지 목적과 섞여 불확실이 많습니다.

## 8. 예 / 아니오 / 불확실 판정 기준 초안

아래 순서로 판정합니다. 모든 판단은 **조항 문언**을 기준으로 하며, 사업자 의도는 추정하지 않습니다.

1. **조항인가?** 설명문·사례문이면 `제외`.
2. **권리를 인정하는 형식이 있는가?** 이용자 권리(청약철회, 환불, 해지, 배상, 이의, 소송, 동의 거부, 게시물 처분, 결제수단 선택 등)를 인정하거나, 이 조항이 다루는 법정 권리를 전제하는 문언이 있는지 봅니다.
   - 없고 권리를 부정·배제하거나 사업자 권한만 주면 `아니오`로 하고 직접형 유형을 기록합니다.
3. **제한 장치가 있는가?** 기간, 이용 트리거, 공제·수수료, 지급 수단·시기, 예외, 절차·경로, 분쟁 장소·방식, 간주, 게시 고지, 재량·하위정책, 책임 요건 가중, 이용자 의무 전가, 부수 손실, 해지 효과 이연 중 하나라도 있는지 봅니다. 없으면 `아니오`.
4. **해당 패턴의 최소 조건을 문언만으로 모두 충족하는가?** 충족하면 `예`(4절 각 패턴의 "예 최소 조건").
5. **다음 중 하나면 `불확실`**:
   - 부담의 정도를 판단하려면 문언 밖의 기준(법정 기간, 실제 비용, 업계 관행)이 필요한데 조항만으로 알 수 없다.
   - 장치에 정당한 목적이 문언에 제시되어 있다(보안, 부정 거래 방지, 법령 근거).
   - 공정위 시정 후 문구에서 같은 구조가 받아들여진 사례가 있다(9절 경계 사례).
   - 소멸·제한이 권리행사가 아니라 제재에 결부되어 있다.
   - 조항이 단편이라 구조를 확정할 수 없다.
6. **반례 확인.** 다음이면 장치가 있어도 `아니오`입니다.
   - 법정 기준을 그대로 인용한다.
   - 이용자 선택권이나 사전 고지가 있다.
   - 위약금이 대칭이다.
   - 예외를 구체 사유와 기한으로 한정했다.
   - 이용자에게 유리한 간주다.

억지로 `예`로 분류하지 않습니다. 장치는 보이는데 실제 제한 정도를 말할 수 없으면 `불확실`입니다.

## 10. 현재 데이터만으로 기준을 만들기 어려운 부분

1. **정상 약관의 반례가 없습니다.** 반례는 모두 공정위 시정 후 문구입니다. 비슷한 표현을 쓰지만 문제가 되지 않은 일반 약관은 이번 데이터에 없습니다. 실제 약관 2,752개는 이번 범위에서 라벨링하지 않았습니다.
2. **법정 기준을 비교할 원천이 없습니다.** EP01·EP03·EP04 판정에는 법정 기간·기한이 필요합니다(청약철회 7일, 환급 3영업일, 계약 불일치 3개월, 계속거래 해지). Source Data v1에는 법령 데이터가 없어, 이번에는 공정위 판단 이유에 적힌 기준만 사용했습니다.
3. **부담의 정도를 잴 자료가 없습니다.** 수수료율·위약금·기간의 적정성은 실제 비용·업계 관행 없이 문언만으로 판단하기 어렵습니다. 그래서 이런 조항은 불확실로 두었습니다.
4. **공정위 판단이 사건·시기별로 일관되지 않습니다.** 대표 사례가 고의·중과실 단서와 유보 문구이며, 9절에 정리했습니다. 시정 후 문구는 협의 결과이므로 적법 기준선으로 쓰기 어렵습니다.
5. **조항 맥락이 없습니다.** official 조항은 대부분 문제 부분만 뽑은 발췌입니다(verbatim_example 247, unattributed 208). 같은 약관의 다른 조항(예: 별도 환불 규정)을 볼 수 없어 단편 조항은 불확실로 두었습니다. 예: FTC-2025-09-16-46428-01-1.
6. **분석자 1인 코딩입니다.** 판정자 간 일치도를 측정하지 않았습니다.
7. **데이터 품질 문제가 있습니다.** 다음 3건은 Source Data v2에서 정정 여부를 검토할 대상이며, v1은 수정하지 않았습니다.
   - 조항이 아닌 행 2건(`FTC-2023-10-27-43076-04-3` 민법 설명문, `FTC-2021-01-27-41796-S01-1` 보도자료 사례문)
   - 조항 뒤에 공정위 판단문이 붙은 행 1건(`FTC-2023-11-29-43125-04-1`)
8. **판매자(B2B) 조항이 섞여 있습니다.** terms_party=seller_partner 43건은 소비자보호 법정 기준이 적용되지 않습니다. 같은 패턴 정의를 쓸 수 있는지 불분명합니다.
9. **도메인 경계가 남아 있습니다.** 도메인 판정이 review인 15건과 비전자상거래 사건은 분석하지 않았습니다.

## 11. 학습데이터 라벨링 전에 사람이 결정해야 할 항목

1. **회피패턴 범위**: 약관법 전형 조항인 다음 셋을 회피패턴에 넣을지, 별도 위험유형으로 뺄지 정해야 합니다.
   - EP07(관할·중재)
   - EP09(게시 고지)
   - EP11(책임 요건 가중)
   - 뺀다면 예 판정 {{L_YES}}건 중 이 세 패턴만 붙은 {{EXCL_IMPACT}}건이 예가 아니게 됩니다.
2. **EP11 귀책 기준**: "고의 또는 중과실이 없는 한"을 예로 볼지, 불확실로 볼지 정해야 합니다.
3. **유보 문구 처리**: "법이 허용하는 범위에서", "특별한 규정이 없는 한"이 있으면 판정을 바꾸는지 정해야 합니다.
4. **불확실의 쓰임**: 학습에서 별도 클래스로 둘지, 제외할지, 사람 재검토 큐로만 쓸지 정해야 합니다.
5. **라벨 단위**: 한 조항에 여러 항·호가 묶인 경우(직접형과 회피형이 섞인 {{MIXED}}건) 조항 단위로 라벨할지, 항·호 단위로 나눌지 정해야 합니다.
6. **다중 라벨 정책**: 여러 패턴을 모두 둘지, 주 패턴 하나를 지정할지 정해야 합니다. EP08+EP09처럼 항상 짝으로 나오는 패턴을 합칠지도 함께 정합니다.
7. **판매자(B2B) 조항**: 같은 기준으로 라벨할지, 분리할지 정해야 합니다.
8. **제재형 소멸·opt-out·통지 요건** 등 9절 경계 사례의 방향을 정해야 합니다.
9. **법정 기준표 확정**: EP01·EP03·EP04 판정에 쓸 기간·기한 기준표를 정해야 합니다. 법령 데이터 확보 여부와도 연결됩니다.
10. **시정 후 문구의 쓰임**: '아니오' 예시로 쓸지 정해야 합니다. 경계로 표시한 {{N_BOUNDARY}}건은 별도 취급이 필요합니다.
11. **검토 절차**: 예 {{L_YES}}건과 불확실 {{L_UNC}}건을 두 번째 판정자가 교차 검토할지, 일치도 기준을 둘지 정해야 합니다.
12. **데이터 품질 3건**: Source Data v2에서 정정을 요청할지 정해야 합니다.
