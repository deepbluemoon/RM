## 1. 무엇을 왜 테스트했나

학습 세션이 이미 오프라인 평가(`dataset_work/reports/baseline_v0/ROUND1_REPORT.md`: 누수·과적합·출처별 성능)를 했습니다.
이 테스트는 그와 겹치지 않게 **게이트웨이가 실제로 쓰는 코드 경로**(`app.classifiers.load_classifiers`, `app.main.create_app`)로
불러 다음을 확인했습니다.

1. 적재·재현: 서빙 코드로 불러도 학습 때와 같은 점수가 나오는가
2. 운영 특성: 결정성(판정 캐시 전제), 배치 불변성, 지연·메모리
3. 강건성: 직접 만든 합성 조항으로 길이·시정 문구·계약 유형·제목·512토큰 절단·특이 입력에 대한 반응
4. 게이트웨이 E2E: 별도 앱 인스턴스(포트 없음, 임시 키, Ollama 예열 끔)로 API 계약 확인
5. 참고: 2회차 데이터(06 `direct_legal_detector`) VALIDATION 에서 누수 사건을 뺀 M2 성능

지키는 규칙: 데이터는 읽기만 했고(`dataset_work/` 수정 없음), 06 TEST 는 3회차까지 고정이라 쓰지 않았으며,
공유 Ollama 는 호출하지 않았고, 실행 중인 게이트웨이 설정은 바꾸지 않았습니다.

## 5. 강건성 (직접 만든 합성 조항, `contract_type=ecommerce`)

### 5.1 위험 문구 vs 시정 문구

같은 주제에서 위험 문구와 공정한 문구를 비교했습니다.

| 주제 | M1 위험 | M1 시정 | M2 위험 | M2 시정 |
|---|---|---|---|---|
| 면책 ("어떠한 손해에도 책임 없음" / "고의·과실 시 책임") | 0.916 | **0.879** | 0.899 | **0.668** |
| 환불 불가 / 7일 내 전액 환불 | 0.958 | **0.951** | 0.789 | 0.096 |
| 사전 통지 없이 변경 / 30일 전 개별 통지 | 0.950 | **0.957** | 0.927 | 0.040 |
| 잔여 기간 전액 위약금 / 10% 공제 환급 | 0.980 | **0.978** | 0.886 | **0.546** |
| 이의 제기 불가 / 이의 제기 가능·7일 내 답변 | 0.854 | **0.822** | 0.885 | 0.088 |
| 결제 즉시 청약철회 불가 / 7일 내 청약철회 가능 | 0.970 | **0.976** | 0.816 | 0.020 |

- **M1 은 시정 문구를 전부 위험(0.82~0.98)으로 판정**합니다. 내용이 아니라 주제(책임·환불·위약금)에 반응합니다. eval 의 "시정 후 문구 13개 중 46% 위험 판정"과 같은 현상입니다.
- M2 는 6쌍 중 4쌍을 구분했지만 면책·위약금 시정 문구는 여전히 위법(≥ 0.5)으로 봅니다.

### 5.2 길이 — 가장 심각한 문제

위험 문장 **앞에** 평범한 약관 문장(회원 준수 의무, 고객센터 안내 등)을 하나씩 붙였습니다.

| 앞에 붙인 문장 수 | 0 | 1 | 2 | 3 | 6 |
|---|---|---|---|---|---|
| 면책 — 글자 수 | 51 | 92 | 136 | 171 | 268 |
| 면책 — M1 / M2 | 0.92 / 0.90 | 0.65 / **0.31** | **0.07 / 0.02** | 0.02 / 0.01 | 0.02 / 0.01 |
| 환불 불가 — M1 / M2 | 0.96 / 0.79 | 0.91 / **0.06** | **0.38** / 0.01 | 0.09 / 0.01 | 0.02 / 0.01 |
| 일방 변경 — M1 / M2 | 0.95 / 0.93 | 0.71 / **0.14** | **0.04 / 0.01** | 0.02 / 0.01 | 0.02 / 0.01 |

- 약 130자만 넘어도 두 모델 모두 명백한 위험 문구를 놓칩니다. 뒤에 붙여도 같습니다(6개 주제 모두 M1 ≤ 0.10, M2 ≤ 0.02).
- 실제 약관처럼 항 번호가 있는 조항 — "① 관계 법령 준수 ② 회사는 어떠한 손해에 대하여도 책임을 지지 않습니다 ③ 기타는 운영정책에 따름"(113자, 제목 "책임의 제한") — 이 **M1 0.10, M2 0.07** 로 정상 판정됩니다.
- eval 에서 400자 이상 양성 재현율이 M1 0.22, M2 0.33 인 것과 맞습니다. 실제 계약서 조항 대부분이 이 길이대(eval 음성 중앙값 372자)라 **실전 재현율은 eval 수치보다 크게 낮을 것**입니다.

### 5.3 그 밖의 입력

| 확인 | 결과 |
|---|---|
| 계약 유형 6종 바꾸기 | M1 은 거의 영향 없음(위험 평균 0.94~0.96). M2 는 `general_consumer` 에서 시정 문구 평균이 0.24 → **0.51** 로 올라 오탐 증가 |
| 조 제목 유무(없음 / 주제 제목 / "목적") | 차이 0.00~0.08, 판정 바뀜 없음 |
| 590토큰 중립 문단 + 면책 문장 | 문장이 맨 끝(잘림)이든 맨 앞이든 M1 0.02, M2 0.01 — 절단 이전에 길이 때문에 놓침 |
| 빈 문자열 / 한 글자 / "제1조(목적)" | M1 0.14~0.17, M2 0.07~0.28 (정상) |

### 5.4 서빙 쪽 완화 시도 — 문장·항 단위로 나눠 최댓값 사용 (효과 없음)

긴 조항을 "다." · ①~⑳ · "1." 기준으로 나눠 각각 점수를 매기고 최댓값을 조항 점수로 썼습니다.

| 분할 | 모델 | 방식 | 정밀도 | 재현율 | F1 | 정상 약관 오탐률 |
|---|---|---|---|---|---|---|
| eval | M1 | 통째(현재) | 0.783 | 0.750 | **0.766** | 3.2% |
| eval | M1 | 문장 최댓값 | 0.224 | 0.917 | 0.360 | **77.7%** |
| eval | M2 | 통째(현재) | 0.619 | 0.722 | **0.667** | 1.4% |
| eval | M2 | 문장 최댓값 | 0.130 | 0.917 | 0.228 | **66.5%** |

- 재현율은 오르지만 평범한 약관 문장 대부분을 위험으로 판정합니다(dev 도 같은 경향: 오탐률 1% → 81%).
- 즉 모델은 "짧은 문장 = 위험"을 배웠고, 문장 분할은 이 지름길을 그대로 드러낼 뿐입니다. **서빙 로직으로는 해결되지 않고 데이터 구성을 고쳐야 합니다.**

## 6. 참고 — 2회차 데이터(06) VALIDATION 에서 M2

`workspace/06_model_dataset/direct_legal_detector/validation.jsonl` (68행: 양성 44, 확정 음성 24). `contract_type` 은 06 값(플랫폼·중개·금융)이 모델 입력 체계와 달라 `ecommerce` 로 고정했습니다.

| 범위 | n (양성) | 정밀도 | 재현율 | F1 | AUC |
|---|---|---|---|---|---|
| 전체 | 68 (44) | 0.767 | 0.750 | 0.759 | 0.715 |
| baseline_v0 train·dev 사건 제외 | 33 (9) | 0.333 | 0.556 | 0.417 | 0.639 |

- 68행 중 35행의 사건이 baseline_v0 train·dev 에 있어 **전체 수치는 누수로 부풀어 있습니다**.
- 양성 정의도 다릅니다(v0 = 직접형만, 06 = 법적위험있음, 회피형 포함). 누수를 뺀 AUC 0.64 는 앞선 strong negative 실험(TEST AUC 0.68)과 비슷합니다.
- 음성 24개는 같은 분할 양성의 시정본(짝 구조)이라 오탐 10개는 §5.1 의 "시정 문구 구분 실패"와 같은 현상입니다. 표본이 작아 참고용입니다.
