# 운영 대응 스크립트 매뉴얼

## 실행 원칙

- 경고 감지는 대응 옵션을 표시하는 조건일 뿐 실행 명령이 아니다. 스크립트는 운영자가 대상을 확인하고 대시보드에서 실행을 선택한 경우에만 시작한다.
- 읽기 전용 진단 스크립트도 대상과 수집 내용을 실행 전 대화상자에서 확인한다.
- 실행 보고서, 감사 이력, 컨테이너 로그는 로컬 Node 프로세스로 실행한 대시보드 호스트의 `ops-dashboard/.ops-data/` 아래에 저장한다. 운영 공유 폴더나 원격 시스템으로 자동 전송하지 않는다.
- 로그에는 개인정보와 인증 정보가 포함될 수 있다. 로그 수집은 선택 사항이며, 알려진 패턴을 제한적으로 마스킹해도 완전한 비밀정보 제거를 보장하지 않는다. 공유 전 사람이 결과 파일을 검토한다.

## 스크립트 목록

### 컨테이너 장애 정보 묶음 수집

- 파일: `scripts/collect-container-incident.sh`
- 활성 조건: `OPS-CPU-80-001`, `OPS-MEM-80-001`, `HTTP-5XX-RATE-001`
- 동작: 선택된 컨테이너의 이미지, 상태, 종료 코드, 종료 시각, 재시작 횟수, health 상태를 수집한다. 대화상자에서 선택하면 최근 로그 100줄(최대 256 KiB)도 포함한다.
- 변경 영향: 컨테이너·서비스·데이터를 변경하지 않는다.
- 결과: `ops-dashboard/.ops-data/reports/incident.*/incident.txt`에 권한 제한을 적용해 저장한다. `OPS_DIAGNOSTICS_DIR`로 결과 루트 경로를 바꿀 수 있다.
- 확인·정리: 대시보드에서 파일을 다운로드하고, 개별 보고서를 삭제하거나 수정 후 30일이 지난 보고서를 확인 대화상자 후 정리한다. 알려진 패턴의 로그 마스킹은 완전한 비밀 제거가 아니므로 공유 전 내용을 검토한다.

### Docker 연결 상태 점검

- 파일: `scripts/check-docker-access.sh`
- 활성 조건: `OPS-DOCKER-001`
- 동작: Docker CLI 설치 여부, 클라이언트 버전, 선택된 context, Engine 연결 여부를 확인한다. Engine이 응답하지 않아도 점검 결과를 출력한다.
- 변경 영향: 읽기 전용이며 컨테이너·서비스·데이터를 변경하지 않는다.
- 결과: 점검 결과를 대시보드의 대응 결과 영역에 출력한다. 출력에 Docker endpoint 주소나 비밀 환경변수는 포함하지 않는다.
- 다음 확인: `engine=unreachable`이면 Docker Desktop/Engine 실행 상태, 선택된 context, 사용자 접근 권한을 운영자가 확인한다.

### Compose 서비스 replica 수를 목표값으로 변경

- 파일: `scripts/scale-service.sh`
- 활성 조건: CPU·메모리 경고. MariaDB/MySQL 등 상태 저장 서비스는 서버 정책에서 차단한다.
- 동작: 대시보드에서 사람이 명시적으로 선택하고 확인한 뒤에만 Compose replica를 변경한다. 목표는 현재 수보다 큰 경우만 허용하며, 실제 실행 수→목표 수를 확인창에 표시한다. 실행 전 `preflight-ops.sh`가 환경·서비스 허용 목록·현재 수·최대 20개 안전 상한을 점검한다. 변경 후 replica 개수와 설정된 healthcheck를 최대 `OPS_SCALE_WAIT_SECONDS` 동안 확인한다.
- 변경 영향: 서비스 인스턴스 수가 바뀌며, 해당 서비스의 상태 공유·작업 라우팅·자원 한도를 사전에 확인해야 한다.
- 중단: 사전점검 실패 시 변경하지 않는다. 사후 확인 실패는 자동 롤백하지 않으며, 부분 변경됐을 수 있으므로 현재 인스턴스 수와 서비스 상태를 확인한 뒤 재시도·복구를 사람이 결정한다.

## 화면 동작

- 활성 오류 코드에 해당하는 옵션만 실행 가능하게 표시하고, 다른 옵션은 대기 상태로 둔다.
- 실행 버튼은 실행 대신 검토 대화상자를 연다. 대상·오류 코드·작업 설명을 확인하고 취소하거나 명시적으로 실행한다.
- 로그 포함은 기본 해제다. 로그를 첨부하면 대화상자에서 민감정보 주의사항을 먼저 보여준다.
- 실행 중에는 대응 영역에 진행 상태를, 완료·실패 후에는 결과와 보고서 경로를 표시한다. 짧은 토스트는 알림 용도이며 상세 결과를 대신하지 않는다.
- 스크립트 실행 전에 운영자는 이름과 짧은 선택 근거를 입력한다. 실행 시각·이름·근거·오류 코드·대상·결과·소요 시간·로그 포함 여부는 로컬 감사 이력(`.ops-data/action-audit.jsonl`)과 개별 작업 보고서(`.ops-data/reports/action.*/action-report.txt`)에 기록한다. 실패한 스크립트도 보고서를 만든다. 현재 이름은 직접 입력값이며 인증으로 검증된 계정 ID가 아니다. `OPS_OPERATOR_ID`는 추후 로그인 연동 때 계정 식별자를 연결하기 위한 값이다.
- 실행 이력과 보고서는 대시보드의 대응 영역에서 다시 열 수 있다. 이 기능은 단일 OS 사용자 환경을 전제로 하며 사용자별 로그인·다중 호스트 감사 기능은 제공하지 않는다.

## 보고서 검토 및 런북 개선 흐름

- 생성된 보고서는 `pending_review` 상태로 시작한다. 검토 전용 UI 없이 API `GET /api/reports/<보고서ID>/review`에서 현재 상태를 조회하고, `PUT`으로 검토 결과를 기록할 수 있다. 검토 메타데이터는 보고서별 `review.json`에 0600 권한으로 저장하며, 보고서 다운로드에도 현재 상태와 검토 이력을 덧붙인다. 보고서 삭제·보관 정리 시 메타데이터도 함께 삭제한다.
- 상태는 `pending_review` → `reviewed` 또는 `runbook_update_proposed` → `runbook_updated` 순으로 진행한다. 제안 검토 후 `reviewed`로 돌아갈 수 있으며, 새로운 후속 조치가 생기면 다시 제안할 수 있다. 각 변경에는 검토자와 메모가 필요하고, 이력은 보고서마다 최근 100건까지 남긴다.
- 런북 수정 제안에는 저장소 `docs/` 또는 `ops-dashboard/docs/` 아래 Markdown 경로와 제안 내용을 기록한다. 반영 완료 상태로 바꾸려면 대상 경로와 PR·커밋 등의 참조를 기록한다. 이 흐름은 런북 파일을 자동 수정하거나 PR을 만들지 않는다. 담당자가 제안을 검토해 저장소의 일반 리뷰 절차로 반영한다.
- 검토자 이름은 현재 입력한 문자열이며 인증된 사용자 식별자가 아니다. 로그인 연동 전까지는 로컬 운영 기록으로만 사용한다.
- 상태 갱신 예시: `PUT /api/reports/action.a1b2c3d4/review` JSON 본문 `{"status":"runbook_update_proposed","reviewer":"홍길동","notes":"동일 장애 재발로 절차 보완 필요","runbookPath":"ops-dashboard/docs/response-scripts.md","proposal":"백엔드 확장 전 신규 분석 접수를 일시 중단하고 복구 후 재개한다."}`

## 컨테이너별 로컬 로그 보관

- 로컬 Node 대시보드는 Docker 컨테이너를 조회할 때 실행 중인 각 컨테이너에 `docker logs --follow --timestamps` 수집기를 연결한다. 시작 시에는 최근 1,000줄을 가져오고, 이후에는 파일에 이어 쓴다. 대시보드 재시작 후에는 마지막 로그 시각부터 이어 수집하고 마지막 중복 줄을 한 번 건너뛴다.
- 파일 위치는 `ops-dashboard/.ops-data/logs/<컨테이너명>/<컨테이너ID>.log`다. 컨테이너 이름과 ID를 함께 사용하므로 같은 이름으로 다시 생성된 컨테이너 로그가 섞이지 않는다. 파일은 10 MiB씩 최대 5개로 순환하며 기본 30일이 지난 파일과 커서는 정리한다. `OPS_LOG_ARCHIVE_DIR`, `OPS_LOG_ARCHIVE_MAX_FILE_BYTES`, `OPS_LOG_ARCHIVE_MAX_FILES`, `OPS_LOG_ARCHIVE_RETENTION_DAYS`로 조정할 수 있다.
- 기존 Compose `json-file` 로그(10 MiB × 5개)는 Docker 자체 보관으로 유지된다. 로컬 아카이브는 대시보드가 실행 중일 때 별도로 복사되며 대시보드가 꺼져 있던 동안에는 컨테이너가 제거되기 전에 수집할 수 있어야 한다. 대시보드 시작 시 실행 중 컨테이너별 최근 1,000줄을 보충한다.
- 대시보드가 실행되는 컴퓨터의 디스크에 기록한다. 실행 중인 호스트·Docker context가 원격이면 그 Docker Engine에 로그를 요청하더라도 파일은 대시보드 호스트에 저장된다. 로그에는 민감정보가 있을 수 있으므로 `.ops-data`를 공유하거나 백업하기 전에 접근 권한과 보존 필요성을 확인한다. Docker 컨테이너 로그 드라이버가 `json-file`이 아닌 서비스는 아카이브 수집이 지원되지 않을 수 있다.

## Prometheus 검토 메모

현재 대시보드는 Docker CLI를 통해 컨테이너 상태·CPU·메모리를 5초 주기로 조회하고, 최근 5분 그래프와 임계치 경고를 제공한다. Prometheus를 추가하면 메트릭 이력 보관과 시계열 질의를 별도 구성할 수 있지만, 현재 대시보드의 로그 기능을 대체하지 않는다. 장기 메트릭 보관·교차 컨테이너 쿼리·외부 규칙 알림이 필요해질 때 cAdvisor 및 Prometheus 저장 보존기간, 접근 경계, 대시보드 연동을 별도 이슈로 결정한다.
